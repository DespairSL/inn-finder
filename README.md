# Поиск официального сайта организации по ИНН

Агентный пайплайн на Python: на входе ИНН российской организации, на выходе домен её
официального сайта либо `null`, если сайт не найден или улик недостаточно для уверенного ответа.

```bash
$ python -m inn_finder.cli 7721581040
{"domain": "dadata.ru"}
```

Связка Web Search + LLM. Детерминированный код добывает доказательства,
модель принимает по ним решение. Порогов и подобранных коэффициентов в пути принятия решения
нет.


### Результаты в двух строках

Шесть ИНН, локальная модель `gemma-4-12b`, две архитектуры. Полная таблица и оговорки — в разделе
[Что измерено](#что-измерено).

| | без модели | цепочка | агент |
|---|---|---|---|
| верных из размеченных | 2/2 | **2/2** | 2/2 |
| ложных ответов | 0 | **0** | 0 |
| доля `null` | 0.83 | **0.33** | 0.33 |
| вызовов модели | 0 | **42** | 180 |
| токенов на выходе | 0 | **1 904** | 23 735 |
| секунд на ИНН | 1.0 | **5.0** | 22.4 |

Цепочка отвечает и делает это вчетверо дешевле агента по вызовам, в двенадцать раз по токенам и
вчетверо быстрее - при одинаковом качестве ответов.

## Идея решения

Формально это задача поиска, по сути - задача верификации. Найти кандидатов легко, но трудно доказать, 
что домен принадлежит именно этому юрлицу. Критерий качества несимметричный: null допустимый ответом, 
значит ошибочный домен стоит дороже, чем то что ответа не будет.

Российские организации публикуют ИНН у себя на сайте: в контактах, в оферте, в политике обработки персональных данных.
Поэтому сильнейший сигнал это строка с этим ИНН, физически найденная на домене. 
Это превращает нечёткую задачу в почти детерминированную для заметной доли случаев и делает
качество слабо зависящим от того, насколько умна используемая модель.

Показательный пример. ИНН `7721581040` принадлежит **ООО «Дейта Кью»**,
а сайт называется `dadata.ru`. Название с доменом не совпадает ни буквально, ни через
транслитерацию; в поисковой выдаче по ИНН домена нет вообще — он лежит внутри текста сниппетов
справочников (`Сайт: https://dadata.ru`, `info@dadata.ru`). Ответ получается через: добычу
доменов из текста сниппетов и последующей проверкок ИНН на самом сайте.

## Быстрый старт

```bash
git clone <> && cd inn-finder
python3 -m venv .venv && .venv/bin/pip install -e .
cp .env.example .env          # EXA_API_KEY
.venv/bin/python -m inn_finder.cli 7721581040 --provider none -v
```

Нужен OpenAI-совместимый сервер с моделью — подойдёт llama.cpp, vLLM, SGLang, LM Studio или
Ollama. Адрес и имя модели задаются в `.env` (`LOCAL_LLM_BASE_URL`, `LOCAL_LLM_MODEL`).
Без сервера доступен `--provider none`: только детерминированные сигналы, без модели.

Для веб-поиска нужен ключ Exa (`EXA_API_KEY`, регистрация на exa.ai). Реестров и платных
источников реквизитов проект не использует.


Тесты чистых функций — сеть и модель не нужны:

```bash
.venv/bin/python tests.py
```

## Способы использования

### 1. Один ИНН из командной строки

```bash
.venv/bin/python -m inn_finder.cli 7721581040
{"domain": "dadata.ru"}
```

| флаг | назначение |
|---|---|
| `--mode graph\|agent` | режим принятия решений (по умолчанию `graph`) |
| `--provider local\|none` | работать с моделью или на одних детерминированных сигналах |
| `-v`, `--verbose` | трассировка в stderr: карточка, кандидаты, улики, вызовы модели |
| `--full` | весь `Result` в JSON вместо одного домена |
| `--no-cache` | игнорировать кэш поиска, страниц и ответов модели |
| `--batch ФАЙЛ`, `--concurrency N` | пакетный режим, см. ниже |

После `pip install -e .` доступна и консольная команда: `inn-finder 7721581040`.

### 2. Пакетно — список ИНН, на выходе JSONL

```bash
.venv/bin/python -m inn_finder.cli --batch inns.txt --concurrency 3
printf '7721581040\n7707083893\n' | .venv/bin/python -m inn_finder.cli --batch -
```
```json
{"inn": "7721581040", "domain": "dadata.ru", "proof": "inn_on_site"}
{"inn": "7707083893", "domain": "sberbank.ru", "proof": "corporate_email"}
```

Файл — по одному ИНН в строке, `#` — комментарий, `-` — читать stdin. В поле `inn` возвращается
исходная строка, а не нормализованный номер, чтобы результат можно было сопоставить со входом.
Один упавший ИНН не роняет пакет: он приходит с `domain: null` и причиной.

### 3. Из своего кода

```python
from inn_finder.api import Resolver, resolve_inn

result = await resolve_inn("7721581040")           # разовый вызов
print(result.domain, result.proof, result.confidence)

async with Resolver(provider="local", mode="graph") as resolver:
    one = await resolver.resolve("7721581040")
    many = await resolver.resolve_many(["7721581040", "7707083893"], concurrency=3)
```

`Result` содержит не только домен: `proof`, `confidence`, `reason`, карточку организации, список
кандидатов со всеми уликами, телеметрию вызовов модели и шаги агента — этого достаточно, чтобы
разобрать любой ответ постфактум.

### Ожидаемое время

На холодную один ИНН - **20–70 с** в режиме `graph` и дольше в `agent`. Узкое место - обход страниц кандидатов. 
Поисковые запросы идут параллельно. С прогретым кэшем — доли секунды. Для потока запросов держите один `Resolver` в своём процессе,
а не запускайте CLI на каждый ИНН: он переиспользует кэш поиска и ограничитель частоты.

## Архитектура

```
        ИНН
         │
   ┌─────▼──────────────┐
   │ validate_inn       │  контрольная сумма (10 и 12 знаков)
   └─────┬──────────────┘  мусор отсекается до первого запроса в сеть
         │
   ┌─────▼──────────────┐  DaData при наличии ключа
   │ resolve_org        │  иначе -- регулярка по сниппетам, затем LLM, если её не хватило
   └─────┬──────────────┘  -> наименование, ОГРН, город, ОКВЭД
         │
   ┌─────▼──────────────┐  шаблоны от кода + 2-4 запроса от модели
   │ build_queries      │  (бренд обычно не равен юридическому названию)
   └─────┬──────────────┘
         │
   ┌─────▼──────────────┐  Exa, параллельно, с дисковым кэшем
   │ search             │
   └─────┬──────────────┘
         │
   ┌─────▼──────────────┐  домены из ссылок  +  домены из ТЕКСТА сниппетов
   │ collect_candidates │  (поле «Сайт», корпоративная почта, упоминание)
   └─────┬──────────────┘  справочники и чёрный список -> requires_proof
         │
   ┌─────▼──────────────┐  главная + контакты/о компании/оферта/политика
   │ verify             │  -> поиск ИНН и ОГРН в тексте, доступность,
   └─────┬──────────────┘     детект припаркованного домена, редирект на другой домен
         │
   ┌─────▼──────────────┐  скор НЕ решает исход: он задаёт лишь порядок,
   │ score              │  в котором кандидаты показываются модели
   └─────┬──────────────┘
         │
   ┌─────▼──────────────┐  один вызов: карточка организации + все кандидаты с уликами
   │ decide (LLM)       │  -> {"domain": <из списка> | null, "confidence", "reason"}
   └─────┬──────────────┘
         │
   ┌─────▼──────────────┐  проверки на непротиворечивость, без подобранных порогов
   │ guards             │──────────────────────► домен либо null
   └────────────────────┘
```

### Узлы по порядку

**`validate_inn`** (`inn.py`). Контрольные суммы для 10 знаков (юрлицо) и 12 (ИП). Битый ИНН
отбрасывается мгновенно, без единого сетевого запроса. Длина заодно говорит, ИП это или
организация - и этот факт передаётся модели: у ИП сайт бывает заметно реже. Для ИП разбирается
и другой формат имени: не «ООО «Ромашка»», а «ИП Фамилия Имя Отчество».

**`resolve_org`** (`registry.py`). ИНН — это число; чтобы искать сайт, нужно наименование.

* **DaData** — точное наименование, ОГРН, адрес, ОКВЭД, руководитель, статус.
* **Без ключей** — реквизиты из сниппетов справочников: сначала регуляркой, а если её не
  хватило — маленькой моделью со строгой схемой ответа. Разбираются оба формата имени
  (`ООО «Ромашка»` и `ИП Фамилия Имя Отчество`), выбор формата подсказывает длина ИНН.
  Учитываются **только те сниппеты, где ИНН упомянут буквально** — иначе в карточку попадает
  посторонняя организация.

На примере из задания ветка без ключей полностью восстанавливает карточку
(`ООО «Дейта Кью»`, ОГРН `5077746329876`, Москва) без вызова модели.

**`build_queries`** (`pipeline.py`). Шаблоны, которые работают всегда: сам ИНН в кавычках,
`ИНН … официальный сайт`, наименование, наименование + город. Плюс 2–4 запроса от модели — она
нужна там, где бренд не выводится из юридического названия. Запросы к модели опциональны:
при её отказе остаются шаблоны.

**`search`** (`search.py`). Exa.ai за протоколом `SearchProvider`: пайплайн знает только про
метод `search()`, поэтому другой поисковик — это ещё один класс с тем же методом. Запросы идут
параллельно с ограничителем. Exa отдаёт не короткий сниппет, а текст страницы, что напрямую
кормит добычу доменов. Пустая выдача не кэшируется, чтобы сбой не закрепился навсегда.


**`collect_candidates`** (`pipeline.py`). Два источника доменов:

1. Ссылки из выдачи.
2. **Текст сниппетов.** Сайт компании часто вообще не попадает в выдачу ссылкой: в топе стоят
   справочники, а сам домен лежит у них в сниппете. Различаются три вида упоминания - явное поле
   «Сайт», корпоративная почта и просто упоминание в тексте, веса у них разные.

Справочная страница определяется **структурно**: реквизиты организации в самом URL
(`fbc.ru/inn/7721581040/`, `saby.ru/profile/7721581040-...`), а не по списку доменов — списка на
все справочники рунета не хватит. Статический список известных агрегаторов остаётся как
дополнение.

**`verify`** (`verify.py`). Ядро точности. Для каждого кандидата: загрузка главной, разбор ссылок
из футера, обход страниц с реквизитами (`/contacts`, `/about`, `/oferta`, `/privacy`,
`/rekvizity`), поиск ИНН и ОГРН как отдельных чисел (`(?<!\d)7721581040(?!\d)` - чтобы не поймать
их внутри длинного числа), проверка доступности и детект припаркованного домена. Если
главная редиректит на другой домен, тот добавляется в кандидаты и проверяется тоже.

**`decide`** (`pipeline.py` + `prompts.py`). Единственная точка принятия решения. Модель получает
не сырой HTML, а карточку организации и нумерованный список кандидатов с уликами (~300 токенов
на кандидата) и возвращает один JSON: домен из списка либо `null`.

Кода-арбитра с порогами здесь нет. Скор кандидатов сохранён, но влияет
только на порядок показа: плохой порядок стоит пропущенного ответа, но не может породить ложный.

**`guards`** — три проверки ответа модели. Все три о непротиворечивости, ни одна не является
подобранным числом:

1. выбранный домен обязан быть **из показанного списка** - выдумать домен модель не может;

2. сайт, который не отвечает, и сайт, публикующий **чужой** ИНН (при отсутствии своего), ответом
   быть не могут.

### Два режима

| режим | кто принимает решения | зачем |
|---|---|---|
| `graph` | порядок шагов задаёт код, финальный выбор делает модель | рабочий режим: предсказуем, дёшев, воспроизводим |
| `agent` | ReAct-цикл, модель сама выбирает инструменты и порядок | стенд для сравнения агентных способностей моделей |

Инструменты агента: `search`, `fetch`, `check_company_codes` (та же детерминированная проверка
реквизитов, что и в `graph`) и `finish`. Протокол намеренно **не использует нативный function
calling**: у gemma-совместимых сборок его может не быть, а сравнение честно только при
побайтово одинаковом протоколе. Действие - один JSON-объект в тексте ответа. Транскрипт
пересобирается в одно пользовательское сообщение на каждом шаге.

Оба режима получают одинаковые данные - в частности, агенту в наблюдение `search` явно
выводятся домены, добытые из текста сниппетов. Иначе сравнение измеряло бы качество инструмента,
а не решений модели.

Что бы агент ни назвал, ответ проходит ту же детерминированную проверку, а сырой ответ модели
сохраняется в `raw_llm_answer` — это позволяет отдельно измерить, сколько модель угадывает сама
и сколько ей добавляет страховка.

### Промпты

Инструкции по-английски, данные по-русски.

Модель возвращает домен из показанного списка либо `null`, плюс уверенность **перечислением**
(`high` / `medium` / `low`).
На исход эта уверенность не влияет - она попадает в трассировку, а `confidence` в ответе
вычисляется кодом по классу найденных улик.

В примерах промпта обязательно есть случаи с ответом `null` — в том числе коллизия имён и сайт
с чужим ИНН. Воздержание ставится примерами, не инструкцией.

## Как достигается точность

### Веса сигналов

Скор не решает исход - он задаёт порядок, в котором кандидаты показываются модели, и
вычисляет единственный запрещающий признак (площадка из чёрного списка без подтверждения).

| сигнал | вес | комментарий |
|---|---|---|
| ИНН найден на страницах домена | +100 | доказательство принадлежности |
| ОГРН найден на страницах домена | +55 | |
| справочник указал домен в поле «Сайт» | +38 | |
| корпоративная почта на этом домене | +28 | `info@dadata.ru` |
| домен похож на бренд (с транслитерацией) | +22 | вспомогательный |
| сходство названия с доменом | до +25 | вспомогательный |
| упоминание в справочнике / в сниппете | +12 / +4 | вспомогательный |
| домен встретился в выдаче (за упоминание, не более 4) | +6 | вспомогательный |
| зона `.ru`, и она же среди однокоренных | +6 / +15 | `yandex.ru` против `yandex.com` |
| **на сайте опубликован чужой ИНН** | −60 | только если своего ИНН на сайте нет |
| сайт недоступен или припаркован | −40 / −35 | |

### Правила, дающие несимметричность в пользу `null`

1. **Выбор только из показанного списка.** Домен, которого не было среди кандидатов, не
   принимается ни при каких формулировках ответа.
2. **Чёрный список требует доказательства, а не запрещает.** Для собственного юрлица `ozon.ru`
   или `vk.com` — правильный ответ, поэтому такие домены допускаются в кандидаты, но проходят
   только по реквизитам на сайте либо при полном совпадении с брендом.
3. **Чужой ИНН на сайте — довод против**, но лишь когда своего там нет: на сайте группы компаний
   рядом с нужным юрлицом законно соседствуют другие (так устроен `dadata.ru`).
4. **Недоступный сайт ответом быть не может.**
5. **Справочная страница определяется структурно**, по реквизитам в URL. Страница «Реквизиты» на
   сайте самой компании справочником при этом не считается.
6. **Карточка организации собирается только из тех сниппетов, где ИНН упомянут буквально.**
   Иначе реквизиты приходят от посторонней организации, и дальше пайплайн уверенно ищет сайт не
   той компании — эта ошибка была поймана на живом ИП.

Ни одно из этих правил не является подобранным порогом: все они либо о непротиворечивости
ответа, либо о фактах.

### Уверенность и поле `proof`

Уверенность считается по классу улик, а не по сумме баллов. Сумма слабых признаков легко
переваливает любой порог и начинает выглядеть как доказательство - в отчётах это превращается в
ложный эталон. Поэтому в ответе есть отдельное поле:

| `proof` | `confidence` | что это значит |
|---|---|---|
| `inn_on_site` | 0.97 | ИНН опубликован на сайте |
| `ogrn_on_site` | 0.93 | ОГРН опубликован на сайте |
| `directory_site_field` | 0.75 | справочник указал домен в поле «Сайт» |
| `corporate_email` | 0.70 | корпоративная почта на этом домене |
| `null` | ≤ 0.5 | подтверждения нет; ответ принят по совокупности косвенных признаков |

## Подключение модели

Клиент говорит по OpenAI-совместимому `/chat/completions`, поэтому подойдёт любой сервер:
llama.cpp, vLLM, SGLang, LM Studio, Ollama. Проверено на llama.cpp с `gemma-4-12b` (GGUF Q4,
контекст 32K).

```bash
# адрес и модель -- в .env либо в переменных окружения
LOCAL_LLM_BASE_URL=http://localhost:8080/v1 LOCAL_LLM_MODEL=gemma-4-12b \
  .venv/bin/python -m inn_finder.cli 7721581040 --provider local

# без модели -- база отсчёта на одних детерминированных сигналах
.venv/bin/python -m inn_finder.cli 7721581040 --provider none
```


## Что измерено

В проекте два режима: **цепочка** (порядок шагов задаёт код, финальный выбор делает модель) и
**ReAct-агент** (модель сама выбирает инструменты и порядок). Третья конфигурация — без модели вовсе.

```bash
.venv/bin/python -m inn_finder.eval.run_eval \
    --config none:graph --config local:graph --config local:agent
```

Скрипт гоняет один набор ИНН по всем конфигурациям на общем кэше поиска, поэтому различия
относятся к режиму, а не к выдаче. Ответы модели кэшируются вместе с транскриптом шага, так что
повторный запуск воспроизводит ту же траекторию бесплатно.

### Результат прогона (6 ИНН, `gemma-4-12b`, поиск Exa)

| метрика | без модели | цепочка | агент |
|---|---|---|---|
| верных / размечено | 2/2 | **2/2** | 2/2 |
| ошибочный домен | 0 | 0 | 0 |
| домен там, где сайта нет | 0 | 0 | 0 |
| precision по непустым | 1.00 | 1.00 | 1.00 |
| доля `null` | 0.83 | **0.33** | 0.33 |
| подтверждено реестровым кодом | 1 | 1 | 1 |
| вызовов LLM | 0 | **42** | 180 |
| сбоев вызовов | 0 | 0 | 0 |
| валидный JSON с 1-й попытки | — | 1.00 | 1.00 |
| починок формата / невалидных действий | 0 | 0 | 0 |
| повторов действий | — | — | 1 |
| шагов агента (среднее) | — | — | 7.5 из 10 |
| токенов на выходе | 0 | **1 904** | 23 735 |
| секунд на ИНН | 1.0 | **5.0** | 22.4 |

Разбивка по классам случаев — все конфигурации проходят весь размеченный набор:

| класс | без модели | цепочка | агент |
|---|---|---|---|
| `brand-mismatch` | 1/1 | 1/1 | 1/1 |
| `ip` | 1/1 | 1/1 | 1/1 |
| `no-site` | 1/1 | 1/1 | 1/1 |

Выводы:

* **Размечено пока два примера из шести** — один положительный и один негативный. Этого хватает,
  чтобы поймать грубую ошибку, и не хватает, чтобы говорить о качестве.
* **Модель добавляет полноту, а не точность.** Без неё пайплайн отвечает только там, где ИНН
  найден на сайте, — доля `null` 0.83. С цепочкой она падает до 0.33 при нулевом числе ложных
  ответов.
* **Цепочка и агент дают одинаковый результат, но не одинаковой ценой**: 42 вызова против 180,
  1 904 выходных токена против 23 735, 5 секунд на ИНН против 22. Агент тратит 7.5 шага из 10,
  в основном на переформулирование поисковых запросов.
* **12B в 4-битной квантизации безупречно держит протокол**: 1.00 валидного JSON с первой
  попытки, ноль починок формата, ноль невалидных действий на 180 вызовах.

## Устойчивость

* **Кэш на диске** для поиска, загруженных страниц и ответов модели. 
* **Сбои не кэшируются** — ни сетевые, ни модельные. 
* **Ограничитель частоты** вызовов модели (`rps` в конфигурации бэкенда) и ретраи с
  экспоненциальной задержкой и джиттером на `429` и `5xx`.
* **Разбор JSON** терпит markdown-заборы и пояснения вокруг ответа; при невалидном ответе
  делается одна попытка починки с текстом ошибки. Три невалидных ответа подряд в агентном режиме
  прекращают цикл.

## Конфигурация

Всё через `.env` (см. `.env.example`) или переменные окружения.

| переменная | по умолчанию | назначение |
|---|---|---|
| `EXA_API_KEY` | — | ключ веб-поиска Exa, **обязателен** |
| `EXA_SEARCH_TYPE` | `auto` | режим поиска Exa: `auto`, `keyword`, `neural` |
| `LOCAL_LLM_BASE_URL` | `http://localhost:8000/v1` | адрес локального OpenAI-совместимого сервера |
| `LOCAL_LLM_MODEL` | `gemma-4-12b` | имя модели на локальном сервере |
| `LOCAL_LLM_JSON_MODE` | `none` | `json_object` / `json_schema` / `none` |
| `LOCAL_LLM_SYSTEM_ROLE` | `false` | принимает ли шаблон `role=system` |
| `INN_FINDER_VERIFY_TLS` | `0` | проверка TLS при обходе сайтов (см. ниже) |
| `INN_FINDER_CACHE` | `.cache` | каталог кэша |

Тонкая настройка, менять обычно не нужно:

| переменная | по умолчанию | назначение |
|---|---|---|
| `LOCAL_LLM_API_KEY` | `EMPTY` | токен локального сервера, если он его требует |
| `LOCAL_LLM_RPS` | `1000` | у локальной модели ограничения частоты нет |
| `LOCAL_LLM_TIMEOUT` | `300` | таймаут ответа локальной модели, секунды |

Про `INN_FINDER_VERIFY_TLS`: по умолчанию проверка сертификатов при обходе сайтов-кандидатов
**выключена**, потому что заметная часть российских сайтов работает на сертификатах НУЦ РФ,
которых нет в системном хранилище, - с проверкой они просто недоступны, то есть теряются
правильные ответы. Пайплайн читает публичные страницы и ничего никуда не отправляет, так что
риск ограничен подменой читаемого контента. Значение `1` возвращает проверку.

## Структура проекта

```
inn_finder/
  cli.py            CLI: один ИНН, пакетный режим, трассировка
  api.py            Resolver -- программный интерфейс и пакетная обработка
  pipeline.py       режим graph: граф узлов и правила приёмки ответа
  agent.py          режим agent: ReAct-цикл и инструменты агента
  llm.py            OpenAI-совместимый клиент, JSON с починкой, телеметрия вызовов
  prompts.py        промпты решения, генератора запросов и агента
  registry.py       ИНН -> карточка организации из поисковой выдачи
  search.py         веб-поиск за интерфейсом провайдера (Exa)
  fetch.py          загрузка страниц, извлечение текста и ссылок на реквизиты
  verify.py         поиск ИНН/ОГРН на сайте, скоринг, класс доказательства
  domains.py        eTLD+1, чёрные списки, добыча доменов из сниппетов, транслитерация
  models.py         модели данных и телеметрии (pydantic)
  inn.py            контрольные суммы ИНН
  cache.py          файловый кэш
  ratelimit.py      token bucket
  config.py         конфигурация провайдеров и пайплайна
  eval/
    dataset.json    набор ИНН с эталонами
    run_eval.py     прогон конфигураций и сравнительная таблица
tests.py            тесты чистых функций (сеть и модель не нужны)
```

## Ограничения

* **Поиск платный по запросам** (Exa, 3–6 запросов на один ИНН) и требует ключа. Провайдер
  вынесен за протокол `SearchProvider`, поэтому Serper, Yandex или бесплатный `ddgs` встают на
  его место заменой одной реализации.
* **Организации без сайта**, с представительством только в соцсетях, или ликвидированные дают
  `null` — это ожидаемое поведение, а не ошибка.
* **Холдинг** из нескольких юрлиц с одним общим сайтом вернёт этот общий сайт.
* **Реквизиты картинкой** не находятся.
* **Разметка.** Метрики качества требуют размеченного набора; сейчас в нём два проверенных
  примера — положительный и негативный.
